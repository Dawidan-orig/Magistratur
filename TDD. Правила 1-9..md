Правило 1. Напишите тест для проверки кода, который вы собираетесь написать 
	Если можно написать строку кода, то можно написать и тест, который будет ее проверять И ничто не мешает написать его первым

Правило 2 (Сбстно цикл из законов TDD). Сделайте так, чтобы тест перестал проходить.
	Сделайте так, чтобы он снова начал проходить. Очистите код. 

Правило 3. Не гонитесь за золотом. 
	Не пытаться делать идеально или сложно, наоборот.
	
Правило 4. Пишите самый простой, самый конкретный, самый
вырожденный тест, который не будет пройден.

Правило 5. По возможности обобщайте. 
	По мере того как тесты становятся более конкретными, код становится более универсальным.  (Што)
		Пояснение от нейро:
		**Правило 5 TDD** («По возможности обобщайте») — это принцип эволюции кода: по мере добавления **более конкретных тестов** код **становится более универсальным**, автоматически обобщаясь без сознательного рефакторинга.

```
1. Тест 1 (конкретный): divide(10, 5) → 2  → Код: return 10/5 = 2 ✓
2. Тест 2 (конкретный): divide(15, 5) → 3  → Код: return 15/5 = 3 ✓  
3. Тест 3 (конкретный): divide(9, 3)  → 3  → Код: return a/b (обобщился!)

```
*Всё ещё не понятно, почему это должно работать.*

Правило 6. Если вам кажется, что с кодом что-то не так, то внесите коррективы в проект и только потом продолжайте работу. (Приоритезация рефакторинга)

Правило 7. Полностью протестируйте текущий, более простой случай и только потом переходите к более сложному. 
 
Правило 8. Если для прохождения текущего теста требуется написать слишком много кода, то удалите этот тест и напишите более простой, который будет легче пройти. 
 
 Правило 9. Пошагово следуйте найденному шаблону, который
охватывает тестовое пространство.
